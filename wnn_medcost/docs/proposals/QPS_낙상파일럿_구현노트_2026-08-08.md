## 2.1 환자 연계 — 위너넷 입원환자에서 고른다 (2026-08-08 추가)

**QPS 는 환자 자료를 따로 만들지 않는다.** 사고보고 화면의 환자 칸은 `TBL_IPWON_INFO`(위너넷 기존
입원환자 자료 — 10만 5,975건 / 병원 69곳 / 환자 2만 9,697명, 2024-06~2026-12) **입력검색**이다.

- 등록번호(`CHARTNO`)·성명(`PATNAME`) 부분일치 → 후보 20건. ↑↓·Enter·Esc, 250ms 디바운스.
- 고르면 **성별·나이·병동이 자동으로 채워진다**. 저장되는 것은 등록번호뿐.
- **사고 발생일에 재원 중이던 환자가 맨 위**로 오고 `재원중` 배지가 붙는다(오입력 차단).
  퇴원자를 고르면 안내문이 빨간색으로 바뀐다.
- 목록에 없는 대상(외래·직원 등)은 **직접 입력해도 된다** — 검색을 강제하지 않는다.

**★개인정보**: `JUMINNO` 는 매퍼 SQL 안에서만 쓰이고 **화면·서버 응답으로 나가지 않는다.**
성별(주민번호 7번째 자리 홀짝)과 나이(출생연도 파생: 1·2·5·6→19xx / 3·4·7·8→20xx / 9·0→18xx)만
SQL 이 계산해서 돌려준다. 실측 분포로 규칙을 확인했다(13자리 10만 4,477건).

*[선택 근거]* 환자평가표(`TBL_PATVAL_MST`, 14만 2,917건)도 후보였으나 **환자 식별키가 주민번호뿐이고

## 6.1 잡은 버그 — 화면이 안 뜨거나 검색이 안 되던 원인 (2026-08-08)

**① [찾기]·탭·저장이 전부 무반응 — `qpsFall.jsp` 스크립트가 통째로 죽어 있었다**

```js
sel.onchange = qfReload;            // ✗ qfReload 는 이 아래에서 window 에 할당된다
sel.onchange = function(){ qfReload(); };   // ✓ 호출 시점에 찾게 감싼다
```
연도 셀렉트 초기화(파일 앞쪽)에서 **아직 정의되지 않은 이름을 참조** → `ReferenceError` →
바깥 IIFE 가 중단 → `qfPatOpen`·`qfTab`·`qfIncidentSave` 등 **모든 함수가 window 에 등록되지 않았다.**
증상이 "버튼만 안 먹는다"로 보여 버튼 쪽을 계속 파게 만드는 유형. 확인은 콘솔 한 줄이면 된다:
`typeof window.qfPatOpen` 가 `"undefined"` 면 스크립트가 죽은 것이다.

*[검증 방법]* 로그인 없이 확인하려고 JSP 를 정적 HTML 로 바꿔 톰캣 루트에 올리고(`$.post` 는 스텁),
브라우저로 실제 클릭까지 재현했다 — 함수 등록 → 팝업 열림 → 행 3건 → [선택] → 성별·나이·병동 자동채움.
같은 상황이 또 오면 이 방법이 가장 빠르다(끝나면 테스트 파일은 지울 것).

**② 병원을 바꿔도 옛 병원을 조회 — 화면이 로드 시점 `hospCd` 를 붙들고 있었다**

- 상단 [병원검색]은 **쿠키 `s_hospid`** 를 선택 병원으로 덮어쓴다(top.jsp).
- 그런데 화면 JS 가 `post()` 마다 로드 시점의 `${hospCd}` 를 실어 보내고, 컨트롤러는 위너넷이면
  **파라미터를 우선**하므로 옛 병원이 계속 조회됐다. (경도요양병원 선택 상태인데 위너넷 자료가 나옴)
- **조치**: JS 는 `hospCd` 를 아예 보내지 않는다 → 서버가 매 요청 쿠키를 본다 = 선택 병원과 자동 연계.
- 화면 머리에 **대상 병원 배지**(`🏥 경도요양병원(예천)`)를 띄웠다 — 어느 병원을 보는지 안 보이면
  "왜 검색이 안 되지"가 된다.

**③ [찾기] 팝업이 비어 보이던 것** — 입력칸에 남아 있던 글자로 검색해 0건이었다.
→ 팝업은 **검색어를 비우고** 열어 최근 입원환자를 바로 보여준다. 행마다 **[선택]** 버튼도 넣었다.

**④ ★진짜 원인 — AJAX 응답이 JSON 으로 파싱되지 않았다 (가장 오래 걸린 건)**

서버는 정상 데이터(3079바이트)를 주는데 화면만 0건이었다. 응답 자체를 화면에 찍어보니:

```
응답(string): 원문:{"result":"OK","hosp":{"hospnm":"경도요양병원(예천)","hospcd":"37280…
```

**`(string)`** — 내용은 완벽한데 **문자열**로 온 것. `Content-Type: application/json` 이 안 붙어
jQuery 가 파싱하지 않았고, 그래서 `res.list` 가 `undefined` → **오류 하나 없이 조용히 0건**.

- 화면: `$.post(...)` → `$.ajax({ …, dataType:'json' })` 로 교체
- 서버: 엔드포인트 9개 전부 `produces = "application/json;charset=UTF-8"` 추가
- 기존 화면들(assesCheck.jsp 등)은 원래 `dataType:'json'` 을 쓰고 있어 이 문제가 없었다 — 내가 빠뜨린 것.

**⑤ Level 1 사고가 분자에 잡혔다 — 지표 마스터 SELECT 에 컬럼 3개가 빠져 있었다**

DDL 에 `NUMER_SRC·INCID_GB·MIN_LEVEL` 을 나중에 추가하면서 `selectQpsIndi` 의 SELECT 절에는
안 넣었다. → 서비스가 `minlevel` 을 못 읽어 빈 값이 되고 → 매퍼의 `<if test="minLevel != ''">` 가
꺼져서 **등급 필터 자체가 사라졌다** → 정의는 'Level 2 이상'인데 Level 1 까지 세었다.

실측 확인(경도요양병원, Level 1 사고 1건):

| 조건 | 결과 |
|---|---|
| 필터 없음(버그 상태) | 7월 **1건** ← 잘못 |
| `CAST(...) >= 2` (정상) | **0건** |

*[교훈] 마스터 테이블에 컬럼을 추가하면 그 값을 읽는 SELECT 절도 같이 고쳐야 한다.*
*조건이 `<if>` 안에 있으면 값이 비었을 때 **오류 없이 조용히 조건만 사라진다** — 가장 찾기 어려운 형태다.*

**⑥ 분류별 집계도 같은 등급 필터를 쓴다 (2026-08-08 같은 날 후속)**

분자는 Level 2 이상만 세는데 분류표(장소·손상·유형·부서·연령·시간대)는 전건을 세어
"분자 0 인데 분류표엔 1" 로 어긋났다. **SUNWOO 실물에서 분류표 합계 = 분자였다**
(낙상 1/4분기: 분자 2 = accidenttypeRet 2 = edtPlaceRet 2 = edtTimeRet 2) → `selectBreakdown`
6개 분기 전부에 minLevel 조건 추가. CDATA 안이라 `<if>` 대신
`IFNULL(#{minLevel},'')='' OR CAST(...) >= CAST(#{minLevel} AS UNSIGNED)` 순수 SQL 로.
빈 문자열 코드가 '미상' 대신 빈 칸으로 나오던 것도 `NULLIF(TRIM(..),'')` 로 함께 정리.

**[교훈] 이 세 가지를 순서대로 확인했다면 30분이면 끝났다**:
① `typeof window.함수명` (스크립트가 살아있나) → ② 응답의 `build` 표식 (서버가 반영됐나)
→ ③ `typeof res` (JSON 으로 파싱됐나). 증상만 보고 병원코드·한글인코딩·SQL 을 세 번 오진했다.

## 6.3 분모 자동산출 (2026-08-08)

재원일수 탭에 **[⚙ 입퇴원 자료로 자동계산]** 버튼 — 서버가 `TBL_IPWON_INFO` 로 월별 재원일수를
계산해 **칸만 채운다. 저장은 사람이 [저장]으로**(병원 공식 기준과 다를 수 있어 확인이 전제).

- 산정 기준(화면에도 명시): **입원일 포함·퇴원일 제외**, 당일 입·퇴원 = 1일, **재원중은 오늘까지**.
- *[함정] 같은 입원건이 월 스냅샷(JOBYYMM)마다 반복 등장한다* — 경도 실측 1,213행 = 실제 455건(건당 최대 3행).
  `(CHARTNO, 입원일)` 로 묶고 퇴원일은 스냅샷 중 채워진 값(MAX). 이걸 안 하면 재원일수가 2~3배 부푼다.
- *[함정] '입원일자' 같은 머리글 오염행 실존* → 날짜는 REGEXP 8자리만 인정.
- **한계**: 자료 마지막 월 이후는 퇴원 기록 미반영으로 부풀 수 있다(경도: 재원중 표시 374건).
  그래서 자동 '저장'이 아니라 채우기만 한다.
- 검증(경도 2026, 알고리즘 재현): 455건 → 1월 8,888 / 2월 8,519 / 3월 9,918 / 4월 10,123 /
  5월 11,372 / 6월 11,398 / 7월 11,721 / 8월 2,999(오늘까지). 재원 ~370명 × 30일 규모와 부합.
- 엔드포인트 `/qps/censusCalc.do` (계산만, 저장 없음).
- **✅검증 완료(2026-08-08 21:59)** — 화면 [자동계산] 값 = 사전 검산(알고리즘 재현) **100% 일치**,
  사용자가 확인 후 저장. 실분모 적용 후 욕창 지표: 6월 22/11,398=**1.93‰**, 2분기 28/32,893=**0.85‰**,
  상반기 0.46‰, 연간 0.44‰ — 임시분모(1,000) 때의 22‰가 현실 척도로 내려왔다.
