## 1. QPS 범위 — 실측으로 확정

개발계획서의 "QPS 203건"은 DB에서 그대로 확인됐다:
`T_MENU` WHERE COMPANY='0001'(SRC) AND GRP='QPS' → **메뉴 272행, 서식(CHART_ID) 203종**.

QPS 모듈(GRP='QPS')은 프로그램 좌측 트리 전체이며 8개 대분류로 구성:

| 대분류 | 내용 | 서식 규모 |
|---|---|---|
| 01 QI | QI계획서(10지표)·회의록(낙상7차/손위생6차)·우선순위집계·중간/최종보고서 | 36종 |
| 02 QPS | 연간계획·위원회(내규/회의록)·지표분석목록·**지표정의서 14지표**·**지표분석보고서(지표×분기)**·FMEA·RCA·라운딩점검표·전담자·규정·교육 | 80여 종 |
| 03 감염 | 연간계획·위원회·라운딩(12차+주차별)·직원감염노출(분기)·손위생조사표·감염병환자 | 44종 |
| 04 보고서 | **사고 발생보고서 8종**(환자안전·욕창·감염성질환·직원안전·직원감염노출·유해물질·보안·학대폭력) | 8종 |
| 05 재원등록 | 월별 재원환자수/직원수(=지표 분모) | 1종 |
| 06 만족도 | 안내문·계획서·설문지·결과/지표분석/개선활동 보고서 | 9종 |
| 07 불만고충 | 처리대장·지표분석(반기)·개선결과 | 5종 |

환자만족도, 영상 TAT, 검체 TAT, 투약, 학대및폭력, 직원감염노출, 재택복귀율, 요로감염.

## 2. SUNWOO 시스템의 실제 구조 (역설계 결과)

- **Delphi(FireDAC) 클라이언트 + MSSQL**. 서식 화면은 **Delphi 폼 클래스로 하드코딩**
  (`CLASS_NM`='TfrmQPS_Chart_016_1' 식), DB에는 메뉴 트리(T_MENU)와 입력값만 있다.
- **저장 = 컨트롤 단위 키·값 스냅샷**: `T_PATIENT_CHART_D`(77만 행)에
  (COMPANY, PATIENT_ID, CHART_ID, VER, W_DATE, PAGE_NO, **OBJ_NM**) PK로 컨트롤별 1행 —
  CAPTION/TEXT/CHECKED/DATE/IMG. 문서 헤더는 `T_PATIENT_CHART_M`. 부서형 문서는 PATIENT_ID='master'.
- **지표 수치도 문서 안의 텍스트다**: 낙상 1/4분기 지표분석 실물에서 발생률 "0.67‰",
  분자·분모가 전부 `edt_qrt1`, `edtFallHurt1` 같은 컨트롤 값으로 저장돼 있었다.
  → **자동 집계가 아니라 사람이 채우는 전자문서 캐비닛**이다. 결재는 T_SIGNLINE/T_SIGN_HIST/T_CHART_SIGN.
- 정형 지표 테이블(T_FALLHURT/T_BEDSORE/T_HANDWASH_SURVEY, COL1~COLn 범용 구조)이 있으나
  **이 DB에선 전부 0행** — 실사용은 문서 스냅샷 쪽.
- 회사: 0000 선우 / **0001 SRC** / 1000 SRC재활병원 / 2000 SRC노인전문병원.
  다른 부서용 그룹(QQI-1 등)에 문서 수만 건이 있고, QPS 모듈 자체의 작성 문서는 극소수(4건)
  → **데이터 이관 부담은 사실상 없음. 서식(양식) 재현이 과제의 전부다.**

## 4. 구현 전략 — SUNWOO 방식을 그대로 옮기지 말 것

SUNWOO 방식(폼 하드코딩 + 컨트롤 스냅샷)을 웹으로 직역하면 서식 203종 = JSP 203장이 된다.
계획서가 경계한 바로 그 함정. 대신 **하이브리드**:

### 4.1 지표 데이터 = 정형 테이블 (SUNWOO에 없던 "자동 집계"가 차별점)

- `TBL_QPS_INCIDENT` — 사고 건별(낙상/욕창/환자안전/직원안전/학대폭력/보안/유해물질/감염노출,
  `INCID_GB` 구분). 04 보고서 8종의 입력이 여기로 들어온다.
- `TBL_QPS_MONITOR` — 관찰형(손위생 5-moments, 라운딩 점검).
- `TBL_QPS_SURVEY`/`_ANS` — 만족도 설문. `TBL_QPS_CENSUS` — 월별 재원환자수/직원수(**분모**, 05 메뉴).
- `TBL_QPS_STAT_MST` — 지표×분기(월) 스냅샷: 분자·분모·율 자동 산출 + 확정(마감) 개념.
  → 지표분석보고서(지표×4분기+중간+최종, 트리의 최대 물량)가 **입력이 아니라 출력**이 된다.
  SUNWOO에서 "0.67‰"를 손으로 치던 것을 자동화 — 이것만으로 서식 수십 종이 화면 1장으로 준다.

### 4.2 서술형 문서 = 메타데이터 서식 (계획서·회의록·정의서·FMEA·RCA류)

- `TBL_QPS_FORM_MST`(서식 정의) + `TBL_QPS_FORM_ITEM`(항목 메타) + `TBL_QPS_FORM_DATA`
  (제출본, MySQL JSON 컬럼 — SUNWOO의 OBJ_NM 키·값 구조와 자연스럽게 1:1 대응).
- SUNWOO T_MENU의 (ID, PARENT_ID, IDNAME, CHART_ID, SEQ) 트리를 서식 마스터의 시드로 그대로 사용.
- 첨부·전자서명은 문서전산화 1단계 산출물(canvas 서명) 재사용. 결재는 작성자→확인자 2단계부터.

### 4.3 통계·보고

- ECharts 대시보드(지표별 추이·병동 비교·전월/전분기 대비) + DataTables.
- 분기 지표분석보고서는 evalReport 패턴(고정 양식 + 서술 총평)으로 생성.

### 4.4 DB 근거만으로 화면을 만들 수 있는 범위 (2026-08-08 확인)

**DDL 작성 완료** → [sql/qps/ddl/QPS_DDL_2026-08-08.sql](../../sql/qps/ddl/QPS_DDL_2026-08-08.sql) (지표마스터·분모·사고·관찰·집계·보고서 6개 테이블 + 지표 14종 시드).

| 갈래 | DB 근거만으로 가능? | 근거 |
|---|---|---|
| **지표 계열** (사고 입력 → 분모 → 자동집계 → 분기보고서 → 대시보드) | ✅ **가능. 지금 바로 착수 가능** | 낙상 산식 검산 완료 · 분모 원천(T_PATIENTCNT) 확인 · 집계 축(T_RPT) 확인 |
| **양식 재현 계열** (활동계획서·회의록·FMEA·RCA 등 종이양식형) | ⚠️ **레이아웃은 불가 — 서식당 캡처 1장 필요** | `T_PATIENT_CHART_D`는 (OBJ_NM → 값)만 저장. **표 구조·라벨·페이지 구성은 DB에 없다**(Delphi 폼에만 존재, exe는 패킹) |

**미채록 13종 지표 정의는 화면 개발의 장애물이 아니다** — 지표분석보고서 서식은 지표가 달라도
구조가 동일하다(`cxTextEdit1`=지표명 / `3`=정의 / `4`=분자 / `6`=분모 …). 즉 **화면은 1개**,
지표별 차이는 `TBL_QPS_INDI_MST`의 **행(데이터)**일 뿐이다. 정의 문구는 나중에 UPDATE 하면 된다.

**SUNWOO 화면 패턴(2026-08-08 실물 확인: 「질향상및 환자안전 활동계획서」)의 한계 — 웹에서 답습하지 말 것**

- 9개 `1 Page ~ 9 Page` **탭 = 종이 A4 페이지를 그대로 옮긴 것**. 화면 구성이 인쇄물에 종속.
- 표의 행 수가 고정(우선순위 집계표 5행 등) → 대상이 6건이면 못 쓴다.
- 3페이지 순서도가 **빈 도형 박스**(글자를 사람이 채움) — 데이터가 아니라 그림.
- 점수표(병원미션 연관성·환자안전 관련성 등 6항목 ×10점 = 60점)가 **계산 없이 칸**으로만 존재.

→ 웹 이식 방침: **입력 화면과 인쇄물을 분리한다.** 입력은 한 화면 스크롤 + 행 추가 가능한 표,
출력은 인쇄 CSS(`@page`/`break-after`)로 A4 페이지를 만든다(evalReport 가 이미 쓰는 방식).
점수표는 합계 자동계산, 순서도는 SVG 또는 고정 이미지. **페이지 탭 구조는 옮기지 않는다.**
